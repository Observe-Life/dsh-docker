# 计划：中文技能名支持 + 登录返回键修复

## 目标

两个已拍板的缺陷修复，一次做完：

1. **中文技能名**：DSH 0.2.2-rc.5 四处硬编码只认「小写字母/数字/中横线」的技能名，中文技能名在发现阶段被静默跳过、名册不注入、/手势与网页端角标不识别。经调研拍板为「dsh-docker 构建期锚点补丁」，共 3 处正则替换（客户端补全一处经核实无需改动）；字符类放宽为「Unicode 字母与数字（含中文与全角数字）」，序号符号与 emoji 仍拒绝。
2. **登录返回键**：登录后按浏览器返回键落回登录页而非退出标签页。根因已复现实锤（历史栈 `[/login, /]` + GET /login 对已登录用户无条件出页），归属方为自研登录插件。

## 基线

- 诊断结论与本计划承接 2026-11-24/25 会话调研：四处理解点逐一经源码与编译产物核实；社区插件 dsh-chinese-skill-patch 已评估并排除（复刻官方内部实现、覆盖不到客户端、升级分叉风险）。
- 上游无官方修复（deepseek-harness Discussion #936 仅讨论）；不依赖上游。
- 本容器即 dsh-docker 项目构建的镜像（版本钉 0.2.2-rc.5），登录插件双副本机制（镜像 /plugin → 启动复制到数据卷 @local）。

## 改什么 / 不改什么

**改：**
- 仓库新增 `scripts/apply-chinese-skill-patch.js`（3 处锚点替换，模式与 apply-login-patch.js 相同：锚点恰好一处、原子写回、幂等）。
- 仓库 `Dockerfile`：构建期执行新补丁（两行）。
- 仓库 `README.md`：镜像内容与升级须知各补一条。
- 仓库 `plugin/index.js`（包名 @local/dsh-host-authentication-login）：两处——① GET /login 验签 Cookie，已登录 302 回 `/`（先判 Cookie 再读密钥，密钥异常降级出页并留日志）；② 登录页表单改为后台请求（fetch，body 转 `URLSearchParams` 发 urlencoded）嗅探 303 成功后 `location.replace('./')`（无 JS 回退原生提交）。
- 容器内运行文件同步（lib 三处 + 插件两份副本），使重启/热重载后即时生效。

**不改：**
- DSH 官方其余任何逻辑；登录鉴权协议（Cookie 格式、密钥来源、签发响应 303 保留）；技能文件内容；登录补丁锚点机制。

## 兼容边界（不可破坏）

1. 现有 6 个内置英文技能行为不变（放宽为超集：原合法名仍全部合法）。
2. 无 JS 浏览器登录流程不变（原生表单 POST → 303 → `/`）。
3. Cookie 签发/验证协议不变；302 目标固定 `/`，无开放跳转。
4. 登录跳转补丁与新补丁的锚点校验机制不变（升级期锚点失效→构建失败明说）。

## 测试路线（五项记录）

- **模式**：严格（两任务均为改行为）
- **依据**：本环境总纲用户裁决「新功能、修 bug、改行为一律先写会失败的测试」
- **理由**：正则行为与路由行为均可脚本级断言；端到端有 browser-remote 通道
- **怎么验证**：
  - A：红测试（副本文件断言「中文名通过总校验 / 手势匹配 / 角标匹配」——现状必红）→ 打补丁 → 绿；幂等（脚本跑两遍一致）；锚点计数恒 1。副本 = 三个 lib 文件复制到临时区，不碰运行文件。
  - B：红测试（插件路由单测：已登录 GET /login 应 302——现状 200 红；登录页应含无痕跳转脚本——现状无红）→ 改插件 → 绿；**编码契约锁定**（评审阻断项教训）：登录页后台请求必须转 `URLSearchParams`（urlencoded）——`FormData` 会被 fetch 编码成 multipart 而被服务器 401，双向形状测试锁定；真机端到端（重启后，browser-remote 跑「登录 → 返回」确认历史栈只剩 `[/]`、返回即退出标签页；已登录 GET /login 弹回）。
- **最终验收**（用户参与）：重启后名册出现 4 个中文技能、`/标准开发流程` 直接触发；登录→返回不再卡登录页。

## 任务拆分

- **A1 红**：副本断言三处行为（输入=中文/英文技能名；输出=通过/匹配与否）。
- **A2 实现**：补丁脚本 + Dockerfile + README。
- **A3 绿**：副本补丁后全绿 + 幂等；运行文件应用（生效依赖重启，由用户执行）。
- **B1 红**：插件单测六场景（无 Cookie 出页 / 有效 Cookie 302 / 篡改 Cookie 出页 / 过期 Cookie 出页 / 正确凭据 303 / 错误凭据 401）。
- **B2 实现**：插件两处改动。
- **B3 绿**：单测全绿；两份副本同步；热重载尝试 → 真机端到端。
- **C 收口**：范式检查单自查（P1–P5）→ 派 2 个独立评审子代理（冷读 / 验收对照）→ 按意见迭代。
- **D 收尾**：收尾回执 + git 状态；不提交（等用户点头）。

## 风险与退役线

- 锚点随官方升级漂移 → 构建失败明说，人工核对后更新锚点（项目既有流程）。
- 插件热重载可能因模块 import 缓存不加载新代码 → 试证；无效则依赖用户重启，如实报。
- 退役线：A 无旧路径退役（放宽非替换）；官方将来放宽规则时锚点自然失效提示撤补丁。B 的「GET /login 无条件出页」退役；「原生表单提交」有意保留（无 JS 回退，理由如上）。

C 完成（评审过）→ 收尾回执 → 等用户确认提交与重启。
